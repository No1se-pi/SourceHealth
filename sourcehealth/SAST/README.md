# Лёгкий SAST для SourceHealth

SAST (Static Application Security Testing) ищет подозрительные места **в тексте
исходников, без запуска приложения**. Этот модуль — заготовка для хакатона:
70 правил: поиск возможных секретов, AST-анализ Python, проверки Go/Rust/Java/C/C++
с учётом лексического контекста и текстовые проверки JS/PHP, shell и YAML. Python 3.11+, без pip-зависимостей
во время работы. Версия анализатора — 0.3.0.

## Начать за минуту

Откройте PowerShell в корне SourceHealth и выполните:

```powershell
python -m sourcehealth.SAST . --output temp/sast-report.json
Get-Content -Raw temp/sast-report.json | ConvertFrom-Json
```

Вместо `.` можно указать другую папку, например `"D:\Projects\my-repo"`.
Сканер работает и без Git. Чтобы добавить **уже существующие** метрики Git-активности:

```powershell
python -m sourcehealth.SAST . --with-git --output temp/health-report.json
```

Собственный выходной файл автоматически исключается из повторного сканирования.
Другие старые отчёты исключайте явно или сохраняйте вне анализируемой папки.
Файл JSON — UTF-8; русские строки представлены допустимыми JSON-последовательностями
`\uXXXX`, чтобы вывод работал также в старом Windows PowerShell. JSON-парсер
восстанавливает обычный русский текст.

Коды завершения CLI:

| Код | Значение |
|---|---|
| `0` | Проверка завершилась; без `--fail-on` находки не меняют этот код |
| `1` | Есть находка уровня `--fail-on` или выше |
| `2` | Ошибка, сработал лимит или часть поддерживаемых файлов не проверена |

Для CI: `python -m sourcehealth.SAST . --fail-on high --output temp/sast.json`.
Если есть и находки, и неполнота, приоритет имеет код `2`.
Список параметров: `python -m sourcehealth.SAST --help`.

Каталог правил, выбор проверок и SARIF для CI/редакторов:

```powershell
python -m sourcehealth.SAST --list-rules --output temp/rules.json
python -m sourcehealth.SAST . --disable-rule PY-WEAK-HASH --output temp/sast.json
python -m sourcehealth.SAST . --rules-dir my-trusted-rules --output temp/custom.json
python -m sourcehealth.SAST . --format sarif --output temp/sast.sarif
```

`--disable-rule` можно повторять; неизвестный ID вызывает ошибку. CLI запрещает
отключить все правила. В API `rules=[]` оставлен для служебных сценариев, но такой
результат нельзя использовать как security-оценку. `--rules-dir` **заменяет**
встроенный набор правилами из доверенного каталога оператора.

SARIF сохраняет находки, координаты и полноту проверки, но не исходники. Для
объединённого отчёта с `--with-git` используйте обычный JSON. Формат экспорта основан
на [SARIF 2.1.0 OASIS](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html).

## Подключение к остальному проекту

Публичный API следует принятому в SourceHealth подходу с `to_dict()`:

```python
import json
from sourcehealth.SAST import SASTScanner, ScanConfig
from sourcehealth.git import GitActivityAnalyzer, GitCollector

path = "."
scanner = SASTScanner(ScanConfig(exclude_globs=("temp/*",)))
sast = scanner.scan(path)
activity = GitActivityAnalyzer().analyze(GitCollector().collect(path))

report = {
    "schema_version": "1.0",
    "complete": sast.complete,
    "checks": {
        "sast": sast.to_dict(),
        "git_activity": {"status": "ok", "metrics": activity.to_dict()},
    },
}
print(json.dumps(report, ensure_ascii=False, indent=2))
```

SAST не меняет `GitCollector` и `GitActivityAnalyzer`. Для API достаточно
`SASTScanner().scan(path).to_dict()`; объединение с Git в CLI выполняет `build_report()`.
В API результат SAST возвращается напрямую; CLI оборачивает его в `checks.sast`.

Секреты ищутся во всех поддерживаемых текстовых файлах, включая `.env`, YAML и JSON.
Правила `PY-*` ограничены `.py` и `.pyw`. Набор не исчерпывает все форматы токенов,
в частности отдельного детектора PAT SourceCraft пока нет; возможны находки по энтропии.

**Это эвристики:** формат секрета или подозрительный вызов не доказывает эксплуатацию.
AWS ID сам по себе не является секретной половиной ключа. Работоспособность
credentials по сети не проверяется. `severity` — потенциальная серьёзность,
`confidence` — уверенность в интерпретации шаблона. У правил есть категория,
CWE и, где добавлены, ссылки на документацию в каталоге.

### Что даёт AST для Python

AST — синтаксическое дерево, построенное из текста без исполнения кода. 13 правил
анализируют реальные вызовы: `# eval(data)` и строка `"pickle.loads(data)"` больше
не считаются вызовами. Секреты в комментариях/строках продолжают проверяться.

Поддерживаются многострочные вызовы, `import pickle as p`,
`from pickle import loads as decode`, области функций/lambda/comprehensions,
затенение параметрами и присваиваниями. Некоторые фабрики, например
`requests.Session()` и `flask.Flask()`, позволяют проверить вызовы через переменную.
Безопасный SafeLoader, параметризованный SQL, shell=False, verify=True и
usedforsecurity=False не дают соответствующей находки.

Разрешение имён ограничено: нет межфайлового taint-анализа, исполнения или полной
системы типов. `getattr`, произвольные присваивания aliases, динамические импорты,
`*args`/`**kwargs` и поток выполнения могут скрыть вызов. Переопределённое имя
консервативно теряет библиотечный тип, даже если присваивание расположено ниже.
Явное `pickle.loads` распознаётся и во фрагменте без import: тип объекта не доказан.
У SQL-правила имя метода — эвристика, поэтому confidence=low.

Если интересующий Python-файл не разбирается, включая синтаксис более новой версии
Python, отчёт получает `python_syntax_error`, `complete=false`; секреты сохраняются.
Для JS/TS, PHP, shell и YAML остаются текстовые эвристики: примеры внутри строк
или блочных комментариев могут дать находку. Для Go/Rust/Java/C/C++ используется
отдельный лексический контекст, описанный ниже.

### Go, Rust, Java и C/C++: лексический контекст

По 10 правил на язык. Go — `.go`; Rust — `.rs`; Java — `.java`; C/C++ — `.c`,
`.h`, `.cc`, `.hh`, `.cpp`, `.hpp`, `.cxx`, `.hxx`, `.ipp`, `.tpp`.

| Язык | Основные проверки |
|---|---|
| Go | TLS без проверки, старые версии TLS, MD5/SHA-1/DES, короткий RSA-ключ, shell, отключение экранирования шаблона, SQL-конкатенация/форматирование, права 0777 |
| Rust | Небезопасные настройки reqwest/OpenSSL, MD5/SHA-1, shell, uninitialized, transmute, get_unchecked, set_len |
| Java | MD5/SHA-1, AES без явного режима/ECB, DES/RC4 и другие старые шифры, ObjectInputStream/XMLDecoder, внешние XML-сущности, eval, SQL-конкатенация, запуск процессов |
| C/C++ | gets/strcpy/strcat/sprintf, scanf без ширины строки, динамический формат printf/fprintf, shell, временные файлы, слабая криптография, OpenSSL без проверки |

`code_analysis.py` распознаёт комментарии и строковые/символьные литералы.
Комментарии маскируются пробелами с сохранением координат, а находка не может
начинаться внутри литерала. Поддерживаются многострочные вызовы, Go backticks,
Rust raw strings/lifetimes/вложенные комментарии, Java text blocks, C++ raw strings,
числовые разделители и продолжение `//` через backslash. Секреты в комментариях
и литералах по-прежнему проверяются отдельными текстовыми правилами.

Это **лексический анализ плюс шаблоны, не полный AST этих языков**. Нет системы
типов, разрешения import aliases, анализа потока данных, макросов и препроцессора.
Java Unicode-escapes до токенизации, конкатенация строковых констант и вычисленные
настройки не интерпретируются. Совпадение имени пользовательского метода со
стандартным может дать ложное срабатывание. Пробельные промежутки и аргументы
в шаблонах ограничены по длине; необычная запись может скрыть совпадение.

`RUST-TRANSMUTE`, `RUST-UNCHECKED-INDEX`, `RUST-VEC-SET-LEN` имеют severity/confidence
`low`: это точки ручного аудита инвариантов памяти. Корректный unsafe-код допустим.
Например, документация [get_unchecked](https://doc.rust-lang.org/std/primitive.slice.html#method.get_unchecked)
требует самостоятельно обеспечить границы индекса. `mem::uninitialized`
[устарел](https://doc.rust-lang.org/std/mem/fn.uninitialized.html) и требует замены на
MaybeUninit. Не вычитайте одинаковый штраф из Health Score за любую такую находку.

Лексер запускается только для кандидатов. Незакрытый комментарий/литерал в таком
файле даёт `lexical_error` и `complete=false`. Файлы без кандидатов не проходят
полную синтаксическую валидацию; complete относится к выполненным правилам.

### Энтропия простыми словами

`aaaaaaaaaaaaaaaa` предсказуема: энтропия 0. У строки с разнообразными символами
энтропия выше. Используется формула Шеннона `H = -sum(p * log2(p))`, где `p` — доля
каждого символа. Это количество бит на символ, не общая «сила пароля».

Чтобы не выдавать каждый хеш за секрет, эвристика требует одновременно:

1. Имя присваивания содержит `key`, `token`, `secret`, `password` и подобные слова
   согласно regex в файле правила.
2. Значение состоит из 16–256 символов поддерживаемого алфавита.
3. Энтропия не ниже порога; нет распространённого placeholder вроде `your_example`.

Узнаваемые форматы ключей проверяются независимо от энтропии.
Generic-правило не дублирует уже найденный токен на пересекающемся диапазоне.
Конкретные форматы автоматически проверяются до entropy-правил независимо
от порядка файлов правил.
Короткие/простые пароли, значения со пробелами и нестандартные форматы могут
пропускаться — это сознательная граница лёгкой проверки.

## Добавить своё правило отдельным файлом

В `sourcehealth/SAST/rules/` лежит **один JSON-файл на правило**. Создайте, например,
`71_js_new_function.json` со следующим содержимым:

```json
{
  "id": "JS-NEW-FUNCTION",
  "pattern": "\\bnew\\s+Function\\s*\\(",
  "message": "JavaScript-функция создаётся из строки.",
  "recommendation": "Проверьте источник строки; рассмотрите обычную функцию без динамической компиляции.",
  "severity": "medium",
  "keywords": ["function"],
  "suffixes": [".js", ".jsx", ".ts", ".tsx"]
}
```

Перезапустите команду — файл подключится автоматически. Если используете Docker,
пересоберите образ, потому что правила копируются внутрь при сборке.
Добавьте positive/negative-примеры с новым ID в `tests/fixtures/sast_rules.json`;
запустите `python -m unittest discover -s tests -v`. Для новых механизмов добавьте
отдельные регрессионные тесты.

| Поле | Назначение |
|---|---|
| `id` | Обязательный уникальный ID: заглавные латинские буквы, цифры, `-`, `_` |
| `pattern` | Обязателен для regex-движка; в JSON обратную косую черту нужно удваивать |
| `message` | Обязательное описание возможной проблемы |
| `recommendation` | Обязательное конкретное действие по проверке/исправлению |
| `severity` | `high`, `medium` (по умолчанию) или `low` |
| `keywords` | Быстрый фильтр: хотя бы одно слово должно встретиться без учёта регистра |
| `suffixes` | Расширения с точкой; отсутствует/`[]` — любые текстовые файлы |
| `entropy_threshold` | Число; требует группу `(?P<secret>...)` в regex; `null` отключает |
| `category` | security, secret, injection, deserialization, crypto, configuration, memory |
| `confidence` | high, medium (по умолчанию), low; не меняет severity |
| `cwe` | Необязательный ID вида CWE-79 |
| `references` | Необязательный список HTTPS-ссылок |
| `engine` | regex (старый построчный), text_regex, code_regex либо python_call |
| `language` | Для code_regex: go, rust, java либо cpp; suffixes обязательны |
| `prefilter` | Необязательный regex-фильтр для text_regex/code_regex; его условие должно быть шире основного правила |

Файлы загружаются по имени; префиксы задают порядок каталога.
Неизвестные поля, дубли ID/JSON-полей и сломанные
выражения вызывают понятную ошибку с именем файла вместо молчаливого пропуска.
Правила загружаются один раз при импорте модуля.

Для доверенного набора правил в другой папке:

```python
from sourcehealth.SAST import SASTScanner, load_rules

scanner = SASTScanner(rules=load_rules("my-trusted-rules"))
```

Это **заменяет** встроенный набор. Для дополнения используйте
`rules=(*DEFAULT_RULES, *load_rules("my-trusted-rules"))`.
В Python также можно создавать `Rule(...)` напрямую.

### Многострочное правило для Go/Rust/Java/C++

Проще всего скопировать близкий JSON из `rules/`, изменить ID, pattern, сообщения
и добавить тестовые примеры. Для `code_regex` обязательны language и suffixes.
Pattern должен начинаться с проверяемого имени, например `\bstrcpy`, а не с
пробелов перед ним: по началу совпадения проверяется принадлежность к коду.

У `text_regex` и `code_regex` включён re.MULTILINE: `^`/`$` относятся к границам
строк, но `\s` может включать перенос. Старый `engine=regex` по умолчанию сохраняет
построчный контракт сторонних правил. Для многострочного движка явно выбирайте
нужную семантику пробелов. Слишком длинные строки маскируются и отмечаются в отчёте.

`prefilter` — ускорение, а не самостоятельная проверка. Например, фильтр `true`
безопасен для правила, которое ищет явный `InsecureSkipVerify: true`: отсутствие
подстроки исключает находку. Для CPP-FORMAT-STRING фильтр также допускает комментарии
между именем, скобкой и аргументом; possessive-повторы Python 3.11 предотвращают
лишний перебор. Граница имени в этом фильтре проверяется после самого имени:
так re может быстро искать буквальный префикс. Фильтр, более узкий, чем правило,
способен скрыть проблему — проверяйте переносы, комментарии и безопасные примеры.

### Python-правила без regex

```json
{
  "id": "PY-CUSTOM-LOAD",
  "engine": "python_call",
  "calls": ["legacy.deserialize"],
  "check": "any",
  "suffixes": [".py", ".pyw"],
  "message": "Вызван устаревший десериализатор.",
  "recommendation": "Проверьте доверие к данным и замените десериализатор.",
  "category": "deserialization",
  "cwe": "CWE-502"
}
```

`pattern` отсутствует или равен `""`; `keywords` не нужны: предфильтр строится
по `calls`, включая имена исходных функций в import aliases. В Python-конструкторе
Rule передавайте `pattern=""`. Никакие функции из calls движок не импортирует.

| Поле | Значение |
|---|---|
| calls | Квалифицированные имена; *.execute означает любой метод execute |
| check | Предикат из таблицы ниже |
| argument | Имя keyword-аргумента или позиция с 0, только для equals/dynamic |
| value | Ожидаемый литерал для equals, например true/false |

| Предикат | Условие |
|---|---|
| any | Сам факт распознанного вызова |
| equals | Явный аргумент равен value; True и 1 различаются |
| dynamic | Явный аргумент существует и не является константой AST |
| unsafe_yaml | unsafe_load/unsafe_load_all или Loader/CLoader/UnsafeLoader/CUnsafeLoader |
| weak_hash | MD5/SHA-1, включая hashlib.new; исключает usedforsecurity=False |
| formatted_sql | f-string, %, + или .format с SQL-глаголом прямо в execute |
| jwt_verification | options с verify_signature=False или старый verify=False |

Для нового вида условия добавьте предикат в python_analysis.py, разрешите его
в Rule и напишите тесты. Каждый встроенный JSON-файл имеет positive/negative
пример в `tests/fixtures/sast_rules.json`; тест требует полного покрытия каталога.

JSON не исполняет код, но плохой regex может надолго занять процесс (ReDoS).
Не добавляйте вложенные повторения вроде `(a+)+`, проверяйте худшие случаи.
Таймер Python не прерывает regex посреди вычисления: для недоверенного содержимого
есть внешнее ограничение времени контейнера. У ast.parse также есть ограничения
стека; число узлов ограничивается после разбора, а не вместо внешней изоляции
([Python AST](https://docs.python.org/3/library/ast.html#ast.parse)). Загружать правила, присланные
пользователем сервиса, этим загрузчиком нельзя. Конфиги и правила из проверяемого
репозитория автоматически не читаются.

## Как читать JSON

У каждой находки есть `rule_id`, `severity`, относительный `path`, `line`, `column`,
`message`, `recommendation`, `category`, `confidence`, `cwe`, `engine`.
Строки и колонки начинаются с 1; колонка — в символах,
не байтах. Сами секреты, фрагменты кода и их хеши в отчёт **не включаются**.
Названия файлов сохраняются: не помещайте секреты в имена файлов.

В `checks.sast` также есть:

- `summary`: количество high/medium/low;
- `files_scanned`, `bytes_read`, `entries_seen`, `duration_seconds`;
- `complete`: завершён ли анализ в заявленной области;
- `skipped`: счётчики причин пропусков;
- `rule_ids` и `config`: применённые проверки и лимиты;
- `ruleset_digest`: SHA-256 доверенных правил для сравнения их версий;
- `python_files_parsed`, `code_files_lexed`, `files_with_findings`: дополнительная статистика;
- `diagnostics`: до 100 координат неполноты без текста ошибок/исходников;
- `schema_version`, `analyzer`, `analyzer_version`: контракт, имя и версия движка.

Контракт JSON остаётся 1.0: новые поля добавлены, прежние сохранены. Digest
хеширует правила, а не секреты. При сравнении результатов учитывайте версию
движка, digest и config.

`files_scanned` — число декодированных текстовых файлов, включая частично
обработанные. `bytes_read` учитывает и файлы, впоследствии отклонённые как binary.
`entries_seen` учитывает также каталоги и пропуски. Пропуск исключённого каталога
считается один раз, его внутренние файлы не перечисляются.
`skipped.long_line` считает строки; остальные причины относятся к файлам,
каталогам или одному событию достижения лимита. `finding_limit` консервативно
ставит `complete=false` при достижении порога, даже если это последняя находка.

**`complete=false` нельзя превращать в «проблем нет»**, даже если findings пуст.
`complete=true` также не означает доказанную безопасность: это успешный проход
только поддерживаемой области. Для общего рейтинга отображайте покрытие рядом
с оценкой. `summary` позволяет построить UI и политику штрафов, но сам модуль
не выдумывает интегральный Repo Health Score.

## Производительность и ограничения

Чтение идёт по одному файлу; дерево обходится `os.scandir` без полного списка
путей в памяти. Regex компилируются один раз, перед ними работает фильтр по словам
и расширениям. Набор расширения переиспользуется. Встроенные текстовые правила
выполняют finditer по файлу внутри C-движка стандартного re: Python не перебирает
каждую строку для каждого правила. Индекс строк строится только для находок.
Быстрые предфильтры отбрасывают безопасные аргументы и отсутствующие литералы до
лексического разбора; энтропия считается только для ограниченных кандидатов. AST строится один раз на подходящий файл; если интересующие функции
вообще не упоминаются, разбор не запускается.
Результаты сортируются по пути и позиции; при достижении лимитов выбранное
подмножество зависит от порядка обхода ОС.

| Лимит по умолчанию | Значение |
|---|---|
| Один файл | 1 MiB |
| Суммарное чтение | 512 MiB (при изменении файла возможен 1 дополнительный байт проверки) |
| Текстовые файлы | 10 000 |
| Элементы дерева | 100 000 |
| Глубина | 64 открытых уровня, включая корень |
| Одна строка | 8192 символа |
| Находки | 1000 |
| Узлы AST на Python-файл | 50 000 |
| Время SAST | 30 секунд, кооперативно |

Все лимиты доступны через `ScanConfig`. Часть самых частых настроек доступна
через CLI. Превышение размера, длинные строки, недоступные файлы, неизвестная
кодировка и таймаут отражаются как неполный анализ. Длинные строки учитываются,
если для файла активны regex-правила. AST анализирует файл независимо от этого
строкового лимита. Отсутствие ключевых слов позволяет пропустить regex без потери
его возможных совпадений.

Штатно пропускаются `.git`, `.hg`, `.svn`, `node_modules`, `.venv`, `venv`,
`__pycache__`, `vendor`, `dist`, `build`, ссылки/junction/hardlink и специальные
файлы. Каталоги сравниваются с точным именем на любом уровне.
Поддерживаются UTF-8 с BOM и без него, UTF-16/UTF-32 с BOM и объявленная
через PEP 263 кодировка Python. BOM проверяется до классификации NUL как binary;
другие файлы с NUL считаются бинарными. Кодировка не угадывается.
CRLF, CR и LF распознаются как переводы строк. Архивы не распаковываются. `.gitignore` не
используется: иначе `.env` можно случайно скрыть от проверки.
Проверяется текущая рабочая копия, **не секреты из истории Git**. Git-метрики
при этом рассчитываются отдельно по истории HEAD.

`--exclude "temp/*"` сравнивается с относительным POSIX-путём через `fnmatchcase`.
Это не синтаксис gitignore: `*` может захватить `/`, отрицания `!` нет. Чтобы
исключить каталог до обхода, укажите и его имя: `--exclude temp --exclude "temp/*"`.

## SourceCraft → контейнеры → общий JSON

Нужны Docker Engine либо Docker Desktop в режиме Linux containers и Python на хосте.
Сначала один раз соберите доверенный образ из корня **SourceHealth**:

```powershell
docker build -f sourcehealth/SAST/Dockerfile -t sourcehealth-sast .
```

Затем запустите проверку публичного репозитория:

```powershell
python -m sourcehealth.SAST.container https://sourcecraft.dev/examples/self-hosted-worker --output temp/sourcecraft-health.json
```

Можно передать и ссылку клонирования вида
`https://git@git.sourcecraft.dev/organization/repository.git`. Формат основан на
[документации SourceCraft](https://vibe.sourcecraft.dev/portal/docs/ru/sourcecraft/operations/repo-clone).
Используется только HTTPS `git.sourcecraft.dev`, без credentials, редиректов и
произвольных хостов. Приватные репозитории не поддерживаются.

Последовательность работы:

1. Оркестратор создаёт уникальный Docker volume.
2. Git-контейнер загружает default branch с полной историей этой ветки.
   Hooks отключены; submodules, LFS-файлы и зависимости не скачиваются/не запускаются.
3. Второй контейнер получает volume только для чтения, запускает SAST и Git-метрики
   с `--network=none`.
4. JSON поступает через stdout оркестратору. Контейнеры и volume удаляются в `finally`,
   затем отчёт атомарно сохраняется на хосте.

Оба контейнера работают под UID 10001, с read-only корнем, без capabilities,
с запретом новых привилегий, лимитами 512 MiB RAM, 1 CPU, 128 процессов и tmpfs 64 MiB.
Docker socket и домашние каталоги хоста внутрь не монтируются. Параметры изоляции
описаны в [Docker run](https://docs.docker.com/reference/cli/docker/container/run/).
Исходники инструмента находятся в `/app`, а проверяемые — в `/workspace/repo`;
Python запускается в isolated mode, чтобы проект не подменил импорт сканера.

`--timeout 180` ограничивает **каждую стадию** отдельно, не весь workflow.
При timeout оркестратор принудительно удаляет созданные контейнеры. Ошибки
попадают в `error.stage`/`error.code`, не в необработанный вывод Git. При неудачной
очистке `cleanup_pending` перечисляет имена оставшихся ресурсов, `complete=false`.
Если процесс хоста принудительно убит или Docker недоступен, `finally` не может
гарантировать очистку — для сервиса нужен периодический сборщик старых заданий.

Дисковая квота volume **не реализована**. Сетевой контейнер имеет обычный Docker
доступ в сеть, ограничение хоста проверяется приложением, а не firewall. Перед
публичным приёмом произвольных заданий нужны квоты worker-диска, ограничение очереди,
сетевые egress-правила и актуальные версии Docker/Git. Контейнеры разделяют ядро
хоста; это полезная изоляция для прототипа, не абсолютная песочница.
Образ после проверки сохраняется для повторных запусков.

При запуске SAST напрямую на хосте анализируемая папка должна оставаться неизменной:
проверки ссылок не устраняют все гонки замены родительских каталогов. `--with-git`
для недоверенных репозиториев используйте внутри контейнера: существующий
GitCollector собирает историю в память и не имеет собственного жёсткого таймаута.

## Место в ТЗ хакатона

Этот модуль даёт самостоятельный сигнал `checks.sast`. В дальнейшем общий сервис
может объединить его с `checks.git_activity`, данными CI, issues/MR, contributors,
релизами и результатами AppSec SourceCraft. AppSec следует сохранять отдельным
источником и учитывать дубликаты перед расчётом штрафов.

Вес security-компонента, политику штрафов и Repo Health Score 0–100 нужно определить
на уровне общего сервиса. Учитывайте полноту сканирования и ложные срабатывания,
не присваивайте автоматически 100 баллов пустому или неподдерживаемому репозиторию.
Интеграция API AppSec, веб-дашборд и публичный рейтинг не входят в этот SAST-модуль.

### Замер скорости и цель 500 МиБ за 10 секунд

```powershell
python -m sourcehealth.SAST.benchmark --profile polyglot --mib 500 --repeat 3 --output temp/benchmark.json
python -m sourcehealth.SAST.benchmark --profile polyglot-hot --mib 500 --repeat 3 --output temp/benchmark-hot.json
python -m sourcehealth.SAST.benchmark --profile polyglot --mib 500 --file-kib 64 --repeat 3
python -m sourcehealth.SAST.benchmark --files 1000 --repeat 3
python -m sourcehealth.SAST.benchmark --files 300 --repeat 2 --profile python
python -m sourcehealth.SAST.benchmark --files 200 --repeat 2 --profile adversarial
```

`polyglot` создаёт ровно 524 288 000 байт исходников четырёх языков, по умолчанию
500 файлов по 1 МиБ. Имена модулей и функций различаются. В концах первого,
средних и последнего файлов заложены четыре проблемы кода и один синтетический
токен. `verified=true` требует полного объёма, всех файлов, **ровно пяти**
контрольных находок с ожидаемыми ID/путями и отсутствия пропусков. Быстрое
достижение лимита не засчитывается как успешный benchmark; код выхода будет 2.

`polyglot-hot` использует тот же объём и контроли, но часто вызывает интересующие
API с безопасными аргументами. Это проверяет стоимость отбора кандидатов.
`--file-kib 64` увеличивает число файлов до 8000: полезно отдельно измерить
стоимость обхода и открытия. Наборы состоят из текстовых фрагментов; они не
компилируются и не исполняются. Наличие пяти контролей не заменяет тесты всех правил.

По умолчанию временное дерево удаляется. `--directory temp/my-benchmark` сохраняет
его для независимого повторного сканирования; папка должна быть пустой. Явно
сохранённые наборы занимают указанный объём на диске. `--files` относится к старым
профилям clean/python/secrets/adversarial, `--mib` и `--file-kib` — к polyglot.

Измеряется **только scanner.scan()**, без генерации, импорта правил, скачивания
Git, запуска Docker и расчёта Git-метрик. Кеша результатов нет; файловый кеш ОС
не сбрасывается, поэтому это не измерение холодного диска. Сканирование работает
в одном процессе без параллельных workers и сторонних Python-зависимостей.

в каждом большом прогоне найдены все пять контролей, пропусков нет.

Цель достигнута **по медиане на этих синтетических наборах**. Одиночный выброс
15.797 секунды сохранён в таблице: это не гарантия верхней границы 10 секунд.
Системная нагрузка, диск, число файлов, Python AST, сложные литералы и большое
число кандидатов меняют время. Для сервиса измеряйте p95 на реальных репозиториях;
скачивание и Git-историю учитывайте отдельно. При жёстком лимите 10 секунд
передайте `--timeout 10`, но тогда медленный проход вернёт неполный отчёт.

Лимиты benchmark расширены под объём: timeout 120 секунд, число файлов и байтов
с небольшим запасом. Для обычного запуска действуют 512 МиБ суммарного чтения,
1 МиБ на файл, 10 000 файлов и 30 секунд. Репозиторий с файлами больше 1 МиБ
может получить complete=false даже при общем размере меньше 500 МиБ.

Во время разработки профиль hot сначала занимал около 38 секунд. Ускорение дали
отбор по литералам аргументов, фильтр динамического printf с учётом комментариев,
быстрый поиск начала токенов, более короткие списки ключевых префиксов и перенос
построчного перебора в native re. Windows-замеры могут колебаться; результаты
снимка v0.2 и v0.3 на clean показывают локальное сравнение, не универсальный коэффициент.

При сканировании самой SourceHealth тестовые фикстуры закономерно дают находки
на искусственных токенах. Исключайте `temp`, если не хотите анализировать сохранённые
benchmark-наборы и старые отчёты. Внешние репозитории со временем меняются.
