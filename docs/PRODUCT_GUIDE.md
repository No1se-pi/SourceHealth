# Руководство по продукту SourceHealth (Product Guide)

> **SourceHealth** — комплексная платформа аудита, мониторинга и объективной оценки здоровья open-source репозиториев и публичных проектов на базе экосистемы **SourceCraft**. Платформа вычисляет детерминированный **Health Score (0–100)**, предоставляет глубокую аналитику кода и истории Git, формирует прозрачные свидетельства (evidence), детерминированные рекомендации и AI-резюме с валидацией заземления (grounding).

## 1. Что такое SourceHealth

**SourceHealth** — это независимая аналитическая система для платформы SourceCraft, решающая фундаментальную задачу оценки качества программных проектов. В отличие от субъективных метрик популярности (лайки, звёзды, форки), SourceHealth оценивает инженерную зрелость репозитория по проверяемым артефактам, исходному коду и истории разработки.

Ключевые принципы продукта:
- **Детерминизм и воспроизводимость:** один и тот же коммит всегда даёт идентичный балл;
- **Отсутствие галлюцинаций в оценке:** скоринг вычисляется математической моделью (`mvp-score-v1.2`), а не генеративной нейросетью;
- **Честность:** отсутствие данных (`NO_DATA`) никогда не приравнивается к нулю или провалу проверки;
- **Действенность (Actionability):** каждый выявленный дефект сопровождается конкретной рекомендацией и ссылкой на факты (evidence);
- **Безопасность нулевого доверия:** код репозитория никогда не исполняется; анализ проводится статически в изолированных песочницах.

## 2. Целевая аудитория и сценарии использования

1. **Разработчики и архитекторы:**
   - Выбор надежных open-source библиотек и зависимостей на платформе SourceCraft;
   - Сравнение альтернативных проектов перед внедрением (`/compare`);
   - Понимание реальной активности и рисков заброшенности проекта.
2. **Мейнтейнеры репозиториев:**
   - Чек-ап инженерного состояния проекта по стандартизированным правилам;
   - Получение пошаговых рекомендаций по улучшению документации, CI/CD и устранению техдолга;
   - Размещение официального бейджа (`/api/v1/badges/{org}/{repo}.svg`) в `README.md`.
3. **Руководители разработки и техлиды:**
   - Мониторинг портфеля корпоративных репозиториев команды;
   - Контроль концентрации знаний (Bus-фактор) и зон ответственности по директориям;
   - Выявление аномалий и резких скачков активности (Integrity audit).
4. **Жюри и эксперты хакатонов / грантов:**
   - Независимая объективная оценка зрелости репозиториев участников;
   - Автоматическая проверка наличия документации, сборки, тестов и чистоты кода.

## 3. Публичный каталог репозиториев

Каталог SourceHealth агрегирует репозитории платформы SourceCraft, извлекая их метаданные, темы (topics), языки программирования и лицензии.
- Каталог доступен всем посетителям без обязательной авторизации;
- Каждый репозиторий представлен карточкой с актуальным статусом анализа, последним вычисленным Health Score, уровнем покрытия (coverage) и ключевыми тегами;
- Репозитории, ещё не прошедшие анализ, отображаются с нейтральным статусом ожидания и предложением запустить первичный аудит.

---

## 4. Поиск по каталогу

Поисковая строка на главной странице поддерживает быстрый поиск по каталогу:
- Поиск осуществляется по названию репозитория (name), слагу (`org/repo`), описанию (description) и организации;
- Поиск регистронезависимый и токенизированный;
- При поиске сохраняется контекст активных фильтров.

---

## 5. Фильтрация

Пользователю доступны срезы каталога по ключевым характеристикам:
- **Язык программирования:** фильтр по основному языку проекта (Python, TypeScript, Go, Rust, C++, Java и др.);
- **Темы и направления (Topics):** выбор предметной области (backend, frontend, cli, machine-learning, security и т.д.);
- **Доступность оценки:** возможность отображения только проектов с рассчитанным Health Score либо всех репозиториев каталога;
- **Минимальный балл:** отбор проектов с высоким показателем здоровья (например, Health $\ge 70$).

---

## 6. Ранжирование и Leaderboard

Таблица лидеров (Leaderboard) на главной странице представляет ранжированный список проектов экосистемы:
- **Основная сортировка:** по детерминированному **Health Score** (от наибольшего к наименьшему);
- **Альтернативные сортировки:**
  - По активности недавней разработки (Recent Activity);
  - По числу звезд/лайков платформы (Popularity).
- **Изоляция популярности от здоровья:** лайки и просмотры ни при каких обстоятельствах не влияют на Health Score;
- **Честная обработка проектов без оценки:** репозитории с недостаточным объёмом данных не получают фиктивный нулевой балл, а корректно помечаются `NO_DATA` и исключаются из числового рейтинга, предотвращая искажение лидерборда.

## 7. Страница репозитория

Страница `/repositories/{org}/{repo}` является визитной карточкой проекта и включает:
- Общую информацию: ссылка на SourceCraft, лицензия, основной язык, описание, теги;
- Виджет последнего статуса здоровья (Health Score) с динамической цветовой индикацией:
  - **Зеленый ($\ge 75$):** высокое качество и зрелость;
  - **Желтый ($50 - 74$):** умеренное состояние, требуются улучшения;
  - **Красный ($< 50$):** проект в критическом состоянии или заброшен;
- Индикатор покрытия метрик (Coverage %);
- Радарную диаграмму по шести категориям;
- Историю предыдущих запусков анализа с возможностью сравнения версий;
- Кнопку запуска повторного анализа (Re-analyze) для актуализации данных.

## 8. Страница детального анализа

Страница `/analyses/{id}` предоставляет исчерпывающий аудиторский отчёт по конкретному прогону:
- Сводный заголовок с коммитом (Git HEAD SHA), датой запуска и временем выполнения;
- Детализация по всем 6 категориям с раскладкой на составные метрики;
- Блок приоритизированных рекомендаций с кнопками раскрытия доказательной базы;
- Интерактивный инспектор свидетельств (Evidence Inspector);
- Блок Deep Git Analytics (графики коммитов, контрибьюторы, владение);
- Виджет проверки целостности данных (Integrity & Anti-gaming);
- Аналитический блок Source Soul;
- AI Executive Summary с возможностью ручного переключения моделей;
- Кнопка скачивания официального отчёта в формате Markdown.

## 9. Шесть обязательных категорий оценки

Методология `mvp-score-v1.2` делит оценку репозитория на 6 ортогональных категорий с фиксированными нормализованными весами:

| Категория | Нормативный вес | Составные внутренние метрики |
|---|:---:|---|
| **Documentation** | **15** | Наличие README, структура разделов (установка, запуск, сборка, тестирование), наличие файла лицензии (License), CONTRIBUTING.md, русскоязычный «Быстрый старт». |
| **CI/CD** | **15** | Наличие конфигурационных файлов пайплайнов (`.github/workflows`, `.gitlab-ci.yml`, SourceCraft CI), частота успешных прогонов (success rate $\ge 80\%$). |
| **Security** | **20** | Официальные дефекты SourceCraft AppSec по критичности: `max(0, 100 - 40×crit - 20×high - 5×med - low)`. Работает через сессионный PAT. При отсутствии PAT — честный `NO_DATA`. |
| **Activity** | **15** | Частота коммитов за последние 30 дней, регулярность активных дней, давность последнего коммита, динамика PR и свежесть релизов. |
| **Issues** | **15** | Доля закрытых задач, время отклика на issues, отсутствие «зависших» багов (stale issues старше 90 дней). При пустом трекере — нейтральный `NO_DATA`. |
| **Code Health** | **20** | Плотность технического долга (TODO/FIXME маркеров на 1000 строк кода), возраст старейших маркеров, доля аномально больших файлов, находки локального SAST (AST-сканер, поиск захардкоженных секретов). |

Сумма базовых весов составляет ровно **100 баллов**.

## 10. Семантика NO_DATA и ренормализация

Главный этический и математический инвариант SourceHealth: **`NO_DATA != 0`**.

### Правила обработки отсутствующих данных:
1. Если категория не может быть измерена объективно (например, в репозитории нет трекера Issues, не настроен AppSec, или в проекте нет кода на анализируемых языках), категории присваивается статус `availability: "no_data"`, а её численный балл становится `null`.
2. **Порог допуска к общему Health Score:**
   - Число доступных категорий должно быть **$\ge 3$**;
   - Суммарный нормативный вес доступных категорий должен быть **$\ge 50\%$** от общего веса (100).
3. **Формула ренормализации:**
   Если порог допуска пройден, общий балл вычисляется пропорциональным перевзвешиванием только доступных категорий:
   $$\text{Health Score} = \frac{\sum_{i \in \text{Available}} w_i \times s_i}{\sum_{i \in \text{Available}} w_i}$$
   где $w_i$ — нормативный вес категории, $s_i$ — балл категории (0–100).
4. Если порог допуска не пройден (например, доступна только 1 или 2 категории, либо их суммарный вес $< 50\%$), общий Health Score **не рассчитывается** (`null`), статус отчёта помечается как `partial`, а интерфейс выводит понятное объяснение: *«Недостаточно данных для расчёта общего здоровья»*.

## 11. Source Soul: психологический портрет репозитория

**Source Soul** — инновационный модуль качественной интерпретации характера проекта, дополняющий строгий численный скоринг:
- Определяет «архетип» проекта на основе паттернов коммитов, структуры кода и активности (например: *«Педантичный архитектор»*, *«Спринтер перед дедлайном»*, *«Уютный пет-проект»*, *«Обитель стабильности»*);
- Вычисляет шкалы экспрессии: баланс хаоса и порядка, темп разработки, склонность к комментированию;
- **Строгая изоляция:** алгоритмы Source Soul работают в режиме превью (требуется $\ge 2$ категорий и $\ge 30\%$ веса), но **никогда не влияют на официальный Health Score** и не подменяют официальные категории.

## 12. Детерминированные рекомендации

Каждый отчёт об анализе формирует список конкретных шагов по улучшению проекта:
- **Полная воспроизводимость:** рекомендации генерируются детерминированным правилом (`sourcehealth.recommendations.mvp`), исключающим случайность;
- **Приоритизация:**
  - `Priority 1 (Критический):` устранение уязвимостей безопасности, добавление лицензии, настройка сломанного CI;
  - `Priority 2 (Важный):` создание документации по запуску и сборке, очистка залежавшихся issues, исправление SAST-предупреждений;
  - `Priority 3 (Улучшение):` сокращение TODO-маркеров, структурирование директорий.
- **Привязка к фактам:** каждая рекомендация содержит `evidence_refs` — прямые ссылки на метрики и файлы, вызвавшие срабатывание правила.

## 13. Прозрачность и система свидетельств (Evidence)

SourceHealth реализует концепцию **Auditable Scoring** (аудируемый скоринг):
- Ни один балл не берется «из воздуха»;
- Каждое утверждение системы подкреплено объектом `Evidence` с полями:
  - `id`: уникальный идентификатор свидетельства;
  - `kind`: тип факта (файл, коммит, результат сканирования, HTTP-ответ API);
  - `data`: структурированные факты (путь к файлу, найденный маркер, хэш коммита);
  - `timestamp`: время фиксации.
- Пользователь может раскрыть любую категорию и увидеть сырые подтвержденные данные.

## 14. Глубокая аналитика репозитория (Deep Analytics)

Модуль глубокой аналитики Git-истории и репозитория предоставляет объективную картину процессов разработки и архитектурных рисков:
- **Концентрация контрибьюторов (Contributor Concentration):** анализ распределения коммитов среди ведущих авторов и выявление неравномерности вклада;
- **Оценка устойчивости (Bus Factor Proxy):** выявление степени риска зависимости проекта от единственного ключевого разработчика;
- **Карта владения директориями (Directory Ownership):** анализ изменений по корневым каталогам кодовой базы;
- **Инженерная гигиена (Repository Hygiene):** проверка ключевых файлов сопровождения проекта (`.gitignore`, лицензия, документация, конфигурации CI).

---

## 15. Владение кодом и прокси Bus-фактора

Для оценки устойчивости проекта к уходу ключевых участников SourceHealth вычисляет прокси Bus-фактора и карту владения:
- **Прокси Bus-фактора:**
  - Анализирует распределение коммитов среди участников за последние 90 дней (порог: минимум 5 коммитов);
  - Вычисляет минимальное число разработчиков, внесших более 50% изменений;
  - Значение `1` сигнализирует о критической зависимости проекта от одного человека.
- **Дерево владения (Code Ownership):**
  - Группировка авторства изменений по ключевым директориям проекта;
  - Наглядное отображение того, кто является ведущим контрибьютором конкретных подсистем.
- **Приватность и анонимизация:**
  - В целях защиты персональных данных авторов коммитов нормализованные имена и email детерминированно хешируются через SHA-256 (`_identity(name, email)`);
  - В публичном интерфейсе контрибьюторы отображаются нейтральными идентификаторами: `Contributor 1`, `Contributor 2` и т.д.

## 16. Целостность данных и защита от накруток (Integrity)

Платформа включает встроенную систему детекции аномалий и попыток манипуляции оценкой:
- **Детектируемые сигналы аномалий:**
  - `commit_burst`: неестественный всплеск большого числа мелких коммитов за короткое время;
  - `low_sample_ci`: единичные фиктивные прогоны CI без реальных тестов;
  - `score_jump`: аномально резкий скачок баллов между последовательными коммитами;
  - `coverage_jump`: манипуляции с объёмом анализируемых файлов.
- **Принцип прозрачности:** обнаруженные аномалии не аннулируют расчёт втихую, а выносятся в блок предупреждений аудита (Integrity Flags), информируя пользователей и жюри о подозрительных паттернах.

## 17. Сравнение репозиториев (/compare)

Инструмент сравнительного анализа проектов (`/compare`):
- Позволяет сопоставить два любых репозитория SourceCraft бок о бок;
- Накладывает радарные диаграммы категорий друг на друга;
- Подсвечивает дельту баллов по каждому компоненту (например: *«Репозиторий А надежнее по безопасности на +20, но Репозиторий Б активнее обновляется»*);
- Помогает командам и разработчикам делать обоснованный выбор технологического стека.

## 18. История анализов и динамика изменений

SourceHealth сохраняет историю всех проведённых аудитов:
- Каждый запуск анализа фиксирует неизменяемый снепшот состояния репозитория на момент конкретного коммита;
- График динамики Health Score отображает вектор развития проекта во времени (прогресс или деградация);
- Повторный запуск анализа (Re-analyze) идемпотентен: если коммит не изменился, повторно используется существующий актуальный результат; при появлении новых коммитов создается новая запись истории.

## 21. Свои репозитории SourceCraft

Разработчики могут подключать личные учетные данные SourceCraft для доступа к репозиториям организаций и официальному сканеру AppSec:
- Переход во вкладку `/sourcecraft` после авторизации через Яндекс ID;
- Ввод персонального токена доступа (Personal Access Token, PAT);
- Автоматическая загрузка списка репозиториев пользователя и его организаций;
- Запуск аудита доступен строго для репозиториев с видимостью `public` (`can_analyze = (visibility == 'public')`);
- Приватные и внутренние проекты (`private`/`internal`) отображаются только в активной сессии пользователя для инвентаризации; запуск их анализа заблокирован на уровне бэкенда (`can_analyze = false`, отказ при попытке постановки в очередь);
- Для публичных репозиториев при наличии PAT запускается глубокий анализ с официальным сканированием уязвимостей SourceCraft AppSec.

## 22. Аутентификация через Яндекс ID

Авторизация пользователей реализована по промышленным стандартам безопасности:
- Протокол **OAuth 2.0 Authorization Code Flow с расширением PKCE** (Proof Key for Code Exchange);
- Генерация криптографического `code_verifier` и `code_challenge`;
- Защита от CSRF через криптографический `state` параметр;
- Сессия пользователя сохраняется в защищенном cookie с флагами `HttpOnly`, `SameSite=Lax`, `Secure`.

---

## 23. Жизненный цикл PAT и изоляция секретов

Безопасность учетных данных пользователей является строгим приоритетом архитектуры:
- **Краткосрочная сессионная аренда (Ephemeral Lease):** токен PAT связывается только с активной сессией анализа (`analysis_id`);
- **Шифрование в покое:** PAT шифруется алгоритмом **AES-256-GCM** и хранится исключительно в Redis с жестким TTL (1800 секунд);
- **Нулевая утечка в постоянное хранилище:** токен **никогда** не записывается в базу данных PostgreSQL;
- **Изоляция в логах:** заголовки авторизации и токены перехватываются санитайзерами логирования;
- **Изоляция в очередях:** токен не передается в открытых полезных нагрузках (payload) задач Redis Queue;
- **Удаление при выходе:** при нажатии кнопки Logout связка ключей в Redis немедленно уничтожается.

## 24. Интеграция с официальным SourceCraft AppSec

В системе реализован клиент прямого взаимодействия с официальным сервисом безопасности SourceCraft:
- Обращение к API `https://appsec.sourcecraft.tech` от имени пользователя (по его PAT);
- Итерация по группам дефектов (`/v1/defect-groups`) с пагинацией и контролем лимитов памяти;
- Фильтрация открытых дефектов (`OPEN`, `TRIAGE_IN_PROGRESS`, `TRIAGED_TP`, `FIX_IN_PROGRESS`);
- Раскладка по уровням опасности: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`;
- Включение результатов в категорию **Security** с формированием точных ссылок на дефекты.

## 28. AI-отчёты и аналитические резюме

В дополнение к математическому расчету SourceHealth предоставляет структурированный grounded-отчёт с помощью моделей **Yandex AI**:
- Назначение: формирование понятного для менеджмента и техлида резюме (Executive Summary) с ключевыми выводами;
- **Строгие ограничения:**
  - AI **никогда** не вычисляет и не корректирует Health Score;
  - Входные данные строго ограничены проверенными численными фактами из отчёта анализа;
  - Исходный код проекта в модель не отправляется (защита интеллектуальной собственности);
- **Защита от галлюцинаций (Grounding Check):**
  - Сгенерированный ответ валидируется на соответствие фактическим данным отчёта;
  - Если модель упоминает несуществующие проблемы или противоречит фактам, ответ отбраковывается.

## 29. Селектор AI-моделей (Мозг, Крутой мозг, Мегамозг)

Пользователь независимо выбирает модель и глубину отчёта (`brief`, `detailed`, `expert`). Допустима любая
комбинация, автоматического переключения модели нет. Модели:

1. **«Мозг» (Alice AI LLM Flash):**
   - Быстрая и легкая модель;
   - Моментальная генерация краткой выжимки основных плюсов и минусов проекта;
   - Минимальная задержка ответа.
2. **«Крутой мозг» (YandexGPT 5 Lite):**
   - Сбалансированная модель общего назначения;
   - Развернутый аудит инженерных практик, логичная группировка рекомендаций.
3. **«Мегамозг» (YandexGPT 5.1 Pro):**
   - Старшая флагманская модель глубокого анализа;
   - Детальный архитектурный разбор рисков проекта, анализ долгосрочной поддерживаемости и стратегические советы.

Глубины: краткая — основные выводы и действия до ~10 тыс. знаков; подробная — category analysis,
implementation steps и roadmap до ~20 тыс.; экспертная — максимальный grounded-контекст и технический
план до ~50 тыс. Это budgets, а не требование искусственно заполнять объём.

## 32. Обработка крупных репозиториев (≥ 10 000 файлов)

Для безопасной работы с масштабными кодовыми базами (монорепозитории, крупные библиотеки) реализована строгая система защитных барьеров (Resource Bounds):
- **Лимит файлов:** безопасная обработка репозиториев размером до **10 000 файлов**;
- **Поведение на границе (10 001 файл):**
  - При превышении порога в 10 000 файлов анализ переходит в режим частичного охвата (`partial`);
  - Превышение лимита переводит категорию Code Health в `partial`, coverage снижается, общий Health Score становится `null` (не превращаясь в 0);
- **Таймаут статического анализа (SAST):**
  - Ограничение времени работы SAST-сканера — **30 секунд**;
  - По истечении таймаута сканирование прерывается, сохраняя уже найденные факты без падения всего пайплайна;
- **Лимит объема исходников:** ограничение размера считываемых файлов до 512 МБ суммарно.

## 33. Архитектура масштабирования и безопасная конкурентность

SourceHealth использует проверенную архитектуру безопасного параллелизма:
- **Разделение очередей:**
  - Очередь `analysis`: легковесные платформенные задачи (сбор API-метрик, метаданные, AppSec);
  - Очередь `analysis-code`: ресурсоемкие задачи сканирования кода и Git-истории;
- **Изолированный worker-code:**
  - Процессы `worker-code` запускаются изолированно;
  - Взаимодействие со сканером происходит через запуск одноразового эфемерного Docker-контейнера;
  - Контейнер ограничен по ресурсам: `512m` RAM, `1` vCPU, `128` PIDs, read-only rootfs;
- **Гарантии Single-Flight:**
  - Частичный уникальный индекс PostgreSQL исключает параллельный запуск одинаковых профилей одного репозитория;
  - Механизм консультативных блокировок PostgreSQL (Advisory Locks) предотвращает гонки при распределении задач;
- **Безопасный Outbox:**
  - Задачи сначала надежно фиксируются в статусе `queued` в PostgreSQL, после чего диспетчер передает их в Redis Queue.

## 34. Известные ограничения и Roadmap

Честные границы текущей версии продукта:
- **Анализ закрытых (private/internal) репозиториев не поддерживается:** платформа анализирует исключительно репозитории с видимостью `public`. Если пользователь подключает свой PAT, через него обнаруживаются доступные публичные репозитории его организаций и запускается официальный SourceCraft AppSec, но приватный анализ заблокирован на уровне архитектуры (`can_analyze = false`);
- **Код проекта не компилируется и не запускается:** SourceHealth выполняет исключительно статический анализ и аудит метаданных; запуск чужих тестов или бинарников категорически запрещен политикой безопасности;
- **Официальный AppSec требует валидного PAT:** при отсутствии токена категория Security честно принимает статус `NO_DATA` и исключается из ренормализации (не обнуляя общий скор);
- **Плавающая ошибка заземления AI (`ai_grounding_failed`):** в редких случаях, когда нейросетевая модель Yandex не может строго уложиться в рамки переданных фактов, срабатывает защитный барьер заземления, и возвращается статус ошибки верификации вместо галлюцинированного текста;
- **Дорожная карта (Roadmap):**
  - Поддержка безопасного анализа приватных репозиториев (после реализации доверенного authorization bridge Яндекс ID → SourceCraft permissions и изолированных scoped caches);
  - Добавление генерации PDF-версий отчётов аудита;
  - Поддержка webhook-уведомлений о деградации Health Score для CI/CD пайплайнов;
  - Расширение правил статического анализатора для дополнительных языков (Swift, Kotlin, C#).
