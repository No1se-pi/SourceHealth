# Синхронизация каталога SourceCraft

`catalog-sync` переносит только публичные репозитории из официального `GET /repos` в локальный каталог. Одна команда обрабатывает ограниченное число страниц и после каждой успешно записанной страницы сохраняет `next_page_token` в PostgreSQL. При ошибке следующая попытка продолжает с последнего подтверждённого token; повтор страницы безопасен благодаря уникальным ограничениям репозитория.
Некорректная отдельная строка `GET /repos` пропускается с безопасным operator event `catalog_repository_skipped`; тело ответа и поля строки в лог не попадают, а checkpoint страницы продвигается.

```bash
python -m sourcehealth.application catalog-sync
python -m sourcehealth.application maintain
```

`maintain` сначала обновляет каталог, затем ставит due-репозитории в очередь. Ограничение backlog применяется внутри сервиса планировщика и одинаково защищает `maintain` и `enqueue-due`: число новых запусков не превышает свободную ёмкость `CATALOG_SYNC_QUEUE_LIMIT`. `enqueue-due` может включать sync через `CATALOG_SYNC_ENABLED=true`; по умолчанию интеграция выключена. Основные пределы: `CATALOG_SYNC_PAGE_SIZE`, `CATALOG_SYNC_MAX_PAGES`, `CATALOG_SYNC_QUEUE_LIMIT`, `SCHEDULER_BATCH_SIZE`, `CATALOG_CYCLE_INTERVAL_SECONDS` (по умолчанию 6 часов, минимум 1 час).

Один проход каталога защищён PostgreSQL advisory lock: второй процесс завершается с `catalog_sync_already_running`, не ожидая и не меняя checkpoint. После полного цикла новый обход начинается не раньше `CATALOG_CYCLE_INTERVAL_SECONDS`. Каталог связывает переименования по стабильному `sourcecraft_id` и не стирает известные `likes`, язык или default branch отсутствующими значениями.

## 1. Разделение сбора метаданных и глубокого анализа (Decoupling)

**Критический архитектурный инвариант:** обнаружение метаданных (`catalog discovery`) **не должно** приводить к массовой постановке в очередь тяжёлых анализов (`health analysis`).

### Причина и решение проблемы переполнения очереди:
- **Ранее**: при сохранении репозитория метод `upsert_sourcecraft_repository` обновлял `next_analysis_at = now()`. В результате каждая новая страница публичного каталога мгновенно заполняла очередь планировщика тысячами задач на Docker/Git/SAST анализ, блокируя пользовательские запросы.
- **Теперь**:
  - Для существующих строк в БД дата `next_analysis_at` строго сохраняется неизменной (`next_analysis_at` исключён из полей обновления метаданных).
  - Для вновь обнаруженных репозиториев метаданных `next_analysis_at` остаётся `NULL` (никакой глобальной 365-дневной задержки в коде shared upsert нет). Решение о периодическом анализе принимает исключительно сервис планировщика (`maintain`/`enqueue-due`).
  - Ручной импорт (`POST /api/v1/repositories/import`) не задерживается на 365 дней: он явно ставит задачу в очередь с высоким приоритетом.
  - Синхронизация метаданных (`catalog-sync` и `catalog-bootstrap`) взаимно исключают параллельное выполнение с помощью PostgreSQL advisory lock (`CATALOG_SYNC_LOCK_KEY = 0x534F555243454843`).
  - Благодаря этому база метаданных может масштабироваться до десятков тысяч проектов без создания нагрузки на worker-процессы и Docker.

## 2. Быстрый операторский бутстрап (`catalog-bootstrap`)

Для быстрого наполнения базы метаданными платформы SourceCraft без ожидания медленного циклического планировщика реализована выделенная CLI-команда:

```bash
python -m sourcehealth.application catalog-bootstrap --page-size 100 --max-pages 50 --time-budget 300
```

### Параметры:
- `--page-size` (по умолчанию 100, максимум 100): размер страницы запроса к API SourceCraft.
- `--max-pages` (по умолчанию 50): максимальное количество страниц за один запуск.
- `--time-budget` (в секундах, опционально): лимит времени работы процесса. По истечении лимита команда корректно сохраняет текущий checkpoint и завершается.

### Гарантии безопасности:
- **Чекпоинты на уровне страниц**: каждая успешно полученная и сохранённая страница атомарно фиксирует `next_page_token` в таблице `catalog_sync_state`.
- **Возобновляемость**: прерывание команды (Ctrl+C, SIGTERM, time budget) или временный сетевой сбой сохраняют последний подтверждённый токен. Следующий запуск автоматически продолжит сбор с того же места.
- **Изоляция от воркеров**: бутстрап **не ставит задачи в очередь** и **не запускает Docker-контейнеры**.
- **Безопасность данных**: собираются только публичные репозитории; сырые тела ответов и токены не логируются.

## 3. Мониторинг состояния каталога (`catalog-status`)

Команда для проверки текущего состояния каталога и операторских метрик:

```bash
python -m sourcehealth.application catalog-status
```

### Пример вывода (JSON без секретов):
```json
{
  "catalog_public_rows": 28605,
  "with_health": 4829,
  "without_health": 23776,
  "with_topics": 28605,
  "without_topics": 0,
  "classifier_version_stale": 0,
  "current_page_checkpoint_present": true,
  "last_completed_at": "2026-09-28T02:15:00Z",
  "cycle_in_progress": false
}
```

Метрики наглядно разделяют:
- `catalog_public_rows`: общий объём обнаруженных метаданных.
- `with_health`: число репозиториев с рассчитанным числовым Health Score.
- `without_health`: число репозиториев со статусом NO_DATA (доступны через поиск и фильтры, но не загромождают дефолтный рейтинг).
- `classifier_version_stale`: число записей с устаревшей версией классификатора тем.

## 4. Пакетная переклассификация тем (`catalog-reclassify-topics`)

После миграций или обновления словарей ключевых слов классификатора (`catalog-topic-v1`) оператор может запустить безопасный бэкфилл:

```bash
python -m sourcehealth.application catalog-reclassify-topics --batch-size 500 --target-version catalog-topic-v1
```

### Свойства команды:
- Использует **исключительно локально сохранённые публичные метаданные** (имя, slug, описание, язык). Внешние вызовы к SourceCraft не производятся.
- Обработка выполняется пакетами (`--batch-size`) в отдельных транзакциях.
- Идемпотентность: проекты с актуальной `topic_classifier_version` пропускаются (если не передан флаг `--force`).
- Безопасна для запуска на базах любого объёма.
