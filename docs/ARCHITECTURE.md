# Архитектура SourceHealth

## Цель текущего слоя

Подсистема `sourcehealth.git` отвечает за получение истории Git и расчёт временных показателей активности.

Главное архитектурное правило:

> **Сначала собираем факты, затем независимо анализируем их.**

Это позволяет не превращать каждый анализатор в набор вызовов `subprocess` и не запускать `git log` повторно для каждой новой метрики.

## Поток данных

```text
Git repository
     │
     │ subprocess: git ...
     ▼
GitCollector
     │
     │ list[Commit]
     ▼
GitActivityAnalyzer
     │
     │ GitActivityMetrics
     ▼
dict / JSON / следующий слой SourceHealth
```

## Компоненты

### `GitCollector`

Файл: `sourcehealth/git/collector.py`.

Ответственность:

- проверить путь;
- убедиться, что каталог является Git-репозиторием;
- определить, существует ли `HEAD`;
- запустить `git log`;
- получить машинно-читаемый вывод;
- распарсить поля;
- создать `Commit`.

Коллектор **не должен**:

- рассчитывать средние значения;
- оценивать здоровье репозитория;
- нормализовать метрики;
- формировать итоговый рейтинг.

### `Commit`

Файл: `sourcehealth/git/models.py`.

Это промежуточная нормализованная модель одного коммита.

```text
сырой вывод Git -> Commit -> любые анализаторы
```

Она нужна, чтобы остальные компоненты не зависели от синтаксиса `git log`.

### `GitActivityAnalyzer`

Файл: `sourcehealth/git/activity.py`.

Ответственность:

- принять `Iterable[Commit]`;
- привести даты к UTC;
- отсортировать коммиты;
- рассчитать временные метрики;
- вернуть `GitActivityMetrics`.

Анализатор **не должен**:

- запускать Git;
- читать репозиторий с диска;
- создавать временные файлы;
- знать, откуда появились `Commit`.

Именно поэтому его удобно тестировать на искусственных данных.

### `GitActivityMetrics`

Неизменяемый dataclass с результатом временного анализа.

Он хранит уже рассчитанные значения и умеет преобразовываться в `dict`.

## Почему история собирается один раз

Плохой вариант архитектуры выглядел бы так:

```text
метрика A -> git log
метрика B -> git log
метрика C -> git log
метрика D -> git log
```

При росте количества анализаторов это приводит к повторной работе и сильной связанности.

Текущий подход:

```text
git log
  │
  ▼
list[Commit]
  ├──> activity analyzer
  ├──> authors analyzer
  ├──> future analyzer
  └──> future analyzer
```

Историю можно переиспользовать.

## Формат обмена с Git

Используется:

```text
%H%x00%an%x00%ae%x00%aI%x00%B
```

NUL-разделитель выбран потому, что `\n` является допустимой частью commit message.

Это защищает парсер от типичного случая:

```text
Subject

Long message body
with multiple lines
```

## Работа со временем

`Commit.datetime` обязан быть timezone-aware.

Перед вычислениями:

```text
datetime с любым UTC offset
            │
            ▼
          UTC
            │
            ▼
      сортировка/сравнение
```

Это важно для репозиториев, где разработчики работают в разных часовых поясах.

## Обработка пустого репозитория

После `git init` репозиторий существует, но `HEAD` ещё не существует.

Это не считается ошибкой.

```text
репозиторий есть + HEAD нет -> []
```

Дальше анализатор сам возвращает пустой набор метрик.

## Ошибки

Ошибки внешнего Git-слоя преобразуются в `GitCollectionError`.

Так остальной проект не обязан разбираться в `FileNotFoundError`, `OSError` и кодах возврата Git.

## Расширение архитектуры

Новые анализаторы желательно строить по тому же принципу:

```python
commits = GitCollector().collect(repo_path)

activity = GitActivityAnalyzer().analyze(commits)
authors = FutureAuthorAnalyzer().analyze(commits)
```

Если для будущей метрики нужны данные, которых в `Commit` нет, лучше:

1. определить, действительно ли данные относятся к истории коммитов;
2. расширить модель или добавить отдельный коллектор;
3. не помещать новый вызов Git внутрь каждого анализатора.

## Что может появиться дальше

Поверх текущего слоя можно добавить:

- анализ авторов и bus factor;
- частоту merge-коммитов;
- churn;
- анализ веток;
- данные GitHub API;
- SAST и линтеры;
- анализ документации;
- поиск секретов;
- нормализацию показателей;
- объединение метрик в итоговый SourceHealth score.
